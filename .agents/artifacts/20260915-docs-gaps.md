# Skillstore docs gap audit

Codebase-vs-docs comparison performed 2026-09-15. Scope: `cmd/root.go`, `main.go`,
`internal/skill/*.go`, `internal/site/*.go`, `internal/site/templates/index.html.tmpl`,
`internal/site/assets/{app.js,style.css}`, `installer/*`, `Dockerfile`, `.dockerignore`,
`examples/.gitlab-ci.yml`, `examples/README.md`, `go.mod`/`go.sum`, `PRODUCT.md`,
`DESIGN.md`, `README.md`, `AGENTS.md`, `.agents/plans/001-skill-marketplace-generator.md`,
and all 17 files under `docs/`. No fixes suggested — gaps only.

---

## Gap 1: `--help` text still describes the removed per-skill detail page

**File(s):** `cmd/root.go` (`rootCmd.Long`)
**Missing in docs:** `docs/operator-guides/installation.md` (documents running `--help`), `docs/developer-guides/pitfalls.md` (documents the single-page architecture)
**Description:** `rootCmd.Long` reads: "skillstore scans a directory of Claude Code skills, each with a SKILL.md file, and generates a static, searchable marketplace site: a card grid, **a detail page per skill**, zip downloads, and npx install commands." This is the literal text every user sees when running `skillstore --help`. It contradicts the actual, deliberate architecture: there is exactly one rendered page (`index.html`); skill detail is a client-side slide-in panel populated from `search-index.json`, not a per-skill HTML page. `docs/developer-guides/pitfalls.md` explicitly documents this as a "don't reintroduce" decision, and `README.md`/`docs/index.md` correctly describe "a slide-in detail panel" — but nothing flags that the CLI's own `--help` output is stale and contradicts both the code's real behavior and the rest of the docs.
**Severity:** High

## Gap 2: Hardcoded footer attribution/branding baked into every generated site

**File(s):** `internal/site/templates/index.html.tmpl` (footer `<p class="trademark">` block)
**Missing in docs:** `docs/operator-guides/configuration.md`, `docs/operator-guides/deployment.md`
**Description:** Every generated `index.html` footer contains fixed, non-configurable markup: a link to `https://gitlab.com/endekasoft/skillstore` labeled "Skillstore v{{.Version}}" and "by `ndkprd`" linking to `https://gitlab.com/endekasoft`. There is no flag, template override, or documented way to change or remove this. `configuration.md` states "Skillstore has no environment variables and no config file... those two flags are the entire config surface," which is technically true but doesn't warn operators that every generated marketplace will carry this specific third-party attribution/branding regardless of who runs the generator or what they're building.
**Severity:** Medium

## Gap 3: `npx skillstore-install` is documented as a working end-to-end flow, but nothing confirms the package is actually published anywhere resolvable by `npx`

**File(s):** `installer/package.json`, `installer/index.js`, `installer/README.md`
**Missing in docs:** `docs/user-guides/browsing-and-installing-skills.md`, `README.md`, `docs/operator-guides/deployment.md`
**Description:** The generated site's install command (`npx skillstore-install <zip-url> --dest ...`) and all user/operator docs present this as something that already works, end to end, for any visitor. `npx` resolves an unscoped package name like `skillstore-install` from the npm registry (or a local link) — nothing in the repo (no publish script, no CI job, no npm token/registry config, no note in `installer/README.md`) indicates the package has been or will be published to npm. The original implementation plan (`.agents/plans/001-skill-marketplace-generator.md`, FAQ/scope) explicitly lists "Publishing the `installer/` package to the npm registry" as **out of scope** ("publishing/versioning is a follow-up"). No doc under `docs/` mentions this precondition, so an operator following the docs as written has no way to know whether the core `npx` install flow will actually function for their site's visitors.
**Severity:** High

## Gap 4: `contributing.md` claims one version string; there are actually two, maintained independently

**File(s):** `internal/site/render.go` (`const Version = "0.1.0"`), `installer/package.json` (`"version": "0.1.0"`)
**Missing in docs:** `docs/developer-guides/contributing.md`
**Description:** `contributing.md`'s "Release process" section states: "`internal/site.Version` (shown in the generated site's footer) is a single hand-edited constant, currently `"0.1.0"`. If you're introducing versioned releases, **that's the one place** the version string is currently sourced from." This is incorrect — `installer/package.json` independently declares its own `"version": "0.1.0"` for the separate `skillstore-install` npm package. The two currently happen to match by coincidence, but nothing keeps them in sync, and the doc's "one place" claim is wrong.
**Severity:** Medium

## Gap 5: Card badge-selection algorithm and the app.js/render.go duplication requirement are undocumented under docs/

**File(s):** `internal/site/render.go` (`cardBadgePriority`, `maxCardBadges`, `pickBadges`), `internal/site/assets/app.js` (`formatMetadataValue`)
**Missing in docs:** `docs/developer-guides/architecture.md`, `docs/developer-guides/standards.md`, or a new reference doc
**Description:** Cards show up to `maxCardBadges` (2) metadata badges chosen via a fixed priority order (`version` → `author` → `license` → `compatibility` → first remaining key alphabetically). `formatMetadataValue` in `app.js` (for the panel) is explicitly meant to mirror the Go-side equivalent in `render.go` used for badges — `AGENTS.md` calls this out ("keep both in sync if the format logic changes") but `AGENTS.md` lives outside the `docs/` tree entirely. None of `docs/developer-guides/*` mention the badge priority list, the 2-badge cap, or the requirement to keep the two formatting implementations in sync — a contributor working only from `docs/` would not know this duplication exists.
**Severity:** Medium

## Gap 6: Frontmatter key-collision precedence (top-level key vs. same key nested under `metadata:`) is undocumented

**File(s):** `internal/skill/parse.go` (`skillFromFields`)
**Missing in docs:** `docs/operator-guides/configuration.md` (the `SKILL.md` format field table)
**Description:** `skillFromFields` first copies every key from a nested `metadata:` map into `Skill.Metadata`, then unconditionally overwrites with every other top-level frontmatter key of the same name (the second loop has no "already set" guard). So if a `SKILL.md` defines both `metadata: { version: "1.0" }` and a top-level `version: "2.0"`, the top-level value silently wins. `configuration.md`'s field table documents that both nested `metadata:` entries and other top-level keys are "folded into the same metadata set," but never states what happens on a same-key collision between the two sources.
**Severity:** Medium

## Gap 7: A non-map `metadata:` value causes silent, unreported data loss

**File(s):** `internal/skill/parse.go` (`coerceMap`, used in `skillFromFields`)
**Missing in docs:** `docs/operator-guides/configuration.md` ("What makes a skill invalid" section)
**Description:** If a `SKILL.md`'s frontmatter has a `metadata:` key whose value is not a YAML mapping (e.g. a plain string, a list, or `null`), `coerceMap` returns `nil`, and the `for k, v := range coerceMap(nested)` loop becomes a no-op — the entire `metadata:` block is silently dropped with no parse error, no warning, and no partial recovery. `configuration.md`'s "What makes a skill invalid" section lists only two failure conditions (missing `SKILL.md`, missing/empty `name`/`description`, or unparsable YAML) and does not mention that a malformed `metadata:` shape is accepted (the skill is *not* skipped) but silently loses that data.
**Severity:** Medium

## Gap 8: Stray non-directory entries under `--skill-dir` are silently ignored with zero log output

**File(s):** `internal/skill/scan.go` (`ScanDir`)
**Missing in docs:** `docs/operator-guides/configuration.md` ("What makes a skill invalid" section), `docs/operator-guides/troubleshooting.md`
**Description:** `ScanDir` iterates `os.ReadDir(root)` and does `if !entry.IsDir() { continue }` — a stray file sitting directly inside `--skill-dir` (e.g. a `README.md`, a stray `.DS_Store`) is skipped with no warning at all, unlike a subdirectory missing `SKILL.md` (which *does* produce a `skill_skipped` warning). Neither `configuration.md` nor `troubleshooting.md` distinguishes this case; a user could reasonably expect any bad entry to at least log something.
**Severity:** Low

---

## Gap 9: An entirely invalid `--skill-dir` produces a misleading `skill_skipped` log line and a silent, successful, empty build

**File(s):** `cmd/root.go` (`runGenerate`), `internal/skill/scan.go` (`ScanDir`)
**Missing in docs:** `docs/operator-guides/troubleshooting.md`
**Description:** When `--skill-dir` itself doesn't exist or can't be read, `ScanDir` returns `(nil, []error{"read skill dir <path>: ..."})` — a single warning, not a fatal error. `runGenerate`'s loop logs every warning identically, as `event=skill_skipped msg="skipping invalid skill"`, regardless of whether it's a genuinely bad individual skill or the whole directory being unreadable. The CLI then proceeds to successfully generate a complete, valid, but **empty** site and **exits 0**. `troubleshooting.md`'s symptom table has a row for "CLI logs `valid_count=0`" pointing at a wrong `--skill-dir`, but doesn't mention that (a) the underlying warning is confusingly labeled as if a specific skill were skipped, or (b) the CLI never fails/exits non-zero in this case.
**Severity:** Medium

## Gap 10: Card display order (alphabetical, case-sensitive) is undocumented

**File(s):** `internal/site/render.go` (`renderIndex`, `sort.Slice(cards, ...)`)
**Missing in docs:** `docs/user-guides/browsing-and-installing-skills.md`
**Description:** Cards are sorted with plain Go string comparison on `Name` (`cards[i].Name < cards[j].Name`), which is byte/ASCII-order, not locale-aware — all-uppercase names sort before any lowercase name (e.g. a skill named `"Vue"` would sort before one named `"bun"`). The user guide never states how skills are ordered in the grid at all, let alone this case-sensitivity quirk.
**Severity:** Low

---

## Gap 11: CLI-level fatal errors bypass the structured zerolog format documented as "everything the CLI emits"

**File(s):** `main.go` (`fmt.Fprintln(os.Stderr, err); os.Exit(1)`)
**Missing in docs:** `docs/operator-guides/troubleshooting.md` ("Log locations" section)
**Description:** `troubleshooting.md` states: "Skillstore logs structured lines to stderr only... There's no separate debug mode; the log output above is everything the CLI emits." In reality, any error returned from `cmd.Execute()` (e.g. `os.RemoveAll`/`os.MkdirAll` failing on `--output-dir`, `site.Render` template errors, `ZipSkillDir` failures, `BuildSearchIndex`/file-write errors) is printed by `main.go` as a single raw `err.Error()` line via `fmt.Fprintln`, not through zerolog's structured/console format. These are genuinely different output shapes an operator would see on stderr, and the doc's "everything the CLI emits [is the structured log format]" claim is incomplete.
**Severity:** Medium

## Gap 12: PRODUCT.md (personas, WCAG 2.1 AA accessibility baseline) is never linked from anywhere under docs/

**File(s):** `PRODUCT.md`; accessibility-relevant implementation in `internal/site/assets/app.js` (focus trap, `inert`, `prefers-reduced-motion` handling) and `internal/site/assets/style.css`
**Missing in docs:** `docs/developer-guides/index.md`, `docs/developer-guides/standards.md`, `docs/index.md`
**Description:** `DESIGN.md` is cross-referenced repeatedly from `docs/developer-guides/*` (stack.md, standards.md, contributing.md), but `PRODUCT.md` — which defines the two user personas, the product purpose, and the explicit "WCAG 2.1 AA baseline" accessibility commitment (full keyboard nav, focus trapping, no color-only signifiers, `prefers-reduced-motion` support) — is not linked or mentioned anywhere in the `docs/` tree. The code demonstrably implements several of these accessibility behaviors (focus trap and `inert` toggling in `app.js`'s `setInertOutsidePanel`/`onPanelKeydown`, `prefers-reduced-motion` handling in both `app.js` and `style.css`), but no doc states the accessibility standard being targeted or why these behaviors exist.
**Severity:** Medium

## Gap 13: Copy-to-clipboard button silently no-ops when `navigator.clipboard` is unavailable

**File(s):** `internal/site/assets/app.js` (`initInstallCopyButton`)
**Missing in docs:** `docs/user-guides/browsing-and-installing-skills.md` ("If something doesn't work" section)
**Description:** `initInstallCopyButton` returns early with `if (!copyButton || !navigator.clipboard) return;` — on a non-secure context (plain HTTP, not `https://` or `localhost`) or an old/restrictive browser, the Copy button is rendered but produces no visible feedback and does nothing when clicked (no error message, no fallback like `document.execCommand`, no disabled state). The user guide's troubleshooting section covers the "Could not load skill data" banner and a non-functional `npx` command, but not a non-functional Copy button.
**Severity:** Low

## Gap 14: Unused `data-total` attribute on the card grid

**File(s):** `internal/site/templates/index.html.tmpl` (`<div id="card-grid" ... data-total="{{len .Skills}}">`), `internal/site/assets/app.js`
**Missing in docs:** none reference it, intentionally or otherwise
**Description:** The template renders a `data-total` attribute on `#card-grid` holding the total skill count, but `app.js` never reads or references `data-total` anywhere. It's dead markup with no documented purpose (e.g., not used for a "showing N of M" UI, not used by search). No doc mentions this attribute as a planned hook or otherwise explains its presence.
**Severity:** Low
